## Problem Statement

O `waydroid_script` está parado desde `d5289cf`, uns 8 meses. O fork em `AlphaLawless/waydroid_script` vai assumir a manutenção.

O problema imediato é o caminho de instalação. O README manda o usuário montar um `venv` na mão, rodar `pip install -r requirements.txt` (três nomes, sem pin, sem lock) e instalar `lzip` pelo gerenciador da distro. Três passos, nenhum reproduzível.

Em distro rolling — o mantenedor usa CachyOS, com Python já em 3.14 — upgrade de Python quebra venv existente. E a dependência de sistema fica fora de qualquer lock, por construção.

## What Makes This Cool

O `lzip` entra no lockfile.

Isso não é conveniência, é uma capacidade que o venv estruturalmente não tem: pixi resolve pacote conda e pacote Python no mesmo grafo de dependência. Verificado nesta sessão, em ambiente descartável:

```
py 3.12.14 | imports OK
lzip 1.21
```

Vale notar que **o `lzip` não está instalado na máquina do mantenedor hoje** — ou seja, o repositório no estado atual não roda sem um passo manual de distro.

Consequência direta: a seção do README que manda `pacman -S lzip` / `apt install lzip` / `dnf install lzip` / `zypper install lzip` desaparece.

E aí vem o passo que torna isso mais do que uma troca de ferramenta. Como o programa exige root de qualquer jeito, dá pra inverter o `check_root()` de parede em porta. O usuário digita `pixi run install gapps` — sem `sudo`, igual em qualquer distro — e o programa se eleva sozinho, carregando o ambiente do pixi consigo.

## Constraints

### Root e propagação de ambiente

- `tools/helper.py:131-134` — `check_root()` aborta se `geteuid() != 0`. Chamado de exatamente dois lugares, `main.py:349` e `main.py:352`, ambos **depois** de `parse_args()`. Isso importa: quando a re-execução acontecer, o argv já foi validado.
- `tools/helper.py:34-40` — `run()` tem `env: Optional[str] = None` na assinatura e repassa `env=env` ao `subprocess.run`. Com o default, o filho herda o ambiente do processo Python, PATH incluso.

  *Nota para quem for mexer:* a anotação `Optional[str]` está **errada** — `subprocess.run(env=)` recebe um mapping, não uma string. Nenhum call site passa `env`, então o bug nunca disparou. Se você for tentado a passar `env=` explicitamente em vez de confiar na herança, corrija a anotação primeiro.

- **A herança vale apenas para os call sites que não reentram no `sudo`.** Três chamadas prefixam `sudo`:
  - `tools/images.py:27` — `run(["sudo", "e2fsck", ...])`
  - `tools/images.py:28` — `run(["sudo", "resize2fs", ...])`
  - `tools/helper.py:57-58` — `Popen(args=["sudo", "waydroid", "shell"])`

  **Precisão importa aqui:** `env_reset` sozinho **preserva** o `PATH` do chamador. Quem o substitui é o `secure_path`, e `secure_path` é política de distro — Debian e Fedora setam, não é universal, e `/etc/sudoers` é 0440 então não foi possível confirmar nesta máquina. Ver OQ-SECUREPATH.

  Se `secure_path` estiver configurado, colocar `e2fsprogs` no `pixi.toml` tem **efeito zero** sobre qual `e2fsck` roda, enquanto esses `sudo` internos existirem.

  O próprio `images.py` mostra que eles são desnecessários: `mount` (L12), `mountpoint` (L20) e `umount` (L21) rodam **sem** `sudo`, no mesmo arquivo, contando com o processo já ser root. Remover o `sudo` de L27-28 e de `helper.py:58` é correção de consistência, não risco — e torna a história do PATH uniforme, independente de `secure_path`.

## Premises

Aceitas na sessão (D6, todas as sete):

1. A dor não é "venv é desatualizado" — são três passos não reproduzíveis. Pixi resolve os três de uma vez.
2. `lzip` no lockfile é o diferencial de pixi sobre uv/venv neste projeto — **provado por probe**. E o inventário de deps de sistema é maior do que o README declara: treze binários, não um.
3. O `sudo` é o ponto de falha central. `sudo pixi run ...` sem tratar PATH ou falha na hora, ou roda com o `lzip`/`tar` do host — e aí o lockfile vira teatro: todo o custo da migração, nenhum do benefício, sem sintoma visível.
4. `pixi.lock` vai commitado. Sem isso a migração não se paga.
5. `flake.nix`, `flake.lock`, `package.nix` e `default.nix` saem. As três primeiras nasceram em `ddaa6b1`; `default.nix` é anterior e foi reescrita por ele. Duas definições do mesmo ambiente, sem CI e sem NixOS na mão do mantenedor, divergem.
6. Toolchain não é o maior risco do projeto. São 30 URLs hardcoded, com o OpenGApps apontando pro SourceForge em builds de 2022 (Android 11) enquanto o default do projeto virou A13. Fora do escopo desta rodada, por decisão explícita — próximo ciclo, não esquecimento.
7. Postura de fork: sucessor de fato (D4).

## Approaches Considered

### Approach A: Wrapper mínimo — descartado

`pixi.toml` + tasks + README reescrito, zero linha de Python. Descartado porque deixa a falha de PATH acontecer em silêncio: o usuário paga o custo da migração e continua rodando as dependências do host, sem nenhum sintoma que denuncie.

### Approach B: Wrapper + guarda — absorvido pelo C

A, mais `check_system_deps()` em `helper.py`, que aborta quando um binário marcado como "deve resolver dentro do env" resolve fora dele, e apenas reporta os demais.

### Approach C: O sudo some do fluxo do usuário — **ESCOLHIDO**

B, mais a inversão de `check_root()`: em vez de `sys.exit(1)` quando `geteuid() != 0`, o programa se re-executa via sudo propagando o ambiente do pixi.

## Recommended Approach

**Approach C.**

### O que C compra sobre B, e o que custa

Isto está explícito porque a diferença é pequena e alguém vai querer reabrir a discussão sem ter o transcript.

**B já resolve as três dores do Problem Statement por inteiro**: lockfile com `lzip` dentro, Python pinado, um comando de setup. O usuário continua digitando `sudo`, e a guarda avisa se o ambiente saiu errado.

**C acrescenta uma coisa só**: o usuário não digita `sudo`, e o erro que a guarda do B detectaria deixa de ser possível para os binários que importam.

**C custa**: um caminho de escalação de privilégio no código, uma flag nova (`--no-elevate`), uma regressão de segurança documentada (derrota o `env_reset` para `PATH`), e uma nota no README.

C foi escolhido porque a D3 definiu pixi como caminho oficial do usuário final. Se essa decisão mudar — se o pixi virar toolchain só de dev — **B passa a ser a escolha certa** e a auto-elevação deve ser removida.

### `check_root()` com elevação

```python
_ELEVATION_SENTINEL = "WAYDROID_SCRIPT_ELEVATED"
_FORWARD_ENV = ("XDG_CACHE_HOME", "WAYDROID_CONFIG")
# Repostos à mão porque o PATH de usuário comum em Debian/Ubuntu não os tem,
# e é o `secure_path` do sudo que hoje os fornece. Ver "O custo escondido".
_SBIN_DIRS = ("/usr/local/sbin", "/usr/sbin", "/sbin")

def _elevated_path() -> str:
    parts = os.environ.get("PATH", "").split(os.pathsep)
    for d in _SBIN_DIRS:
        if d not in parts:
            parts.append(d)
    return os.pathsep.join(p for p in parts if p)

def check_root(allow_elevate: bool = True):
    if os.geteuid() == 0:
        return
    if os.environ.get(_ELEVATION_SENTINEL) == "1":
        Logger.error("Elevação via sudo não resultou em root. Abortando.")
        sys.exit(1)
    if not allow_elevate:
        Logger.error("This script must be run as root. Aborting.")
        sys.exit(1)
    forwarded = [f"{k}={os.environ[k]}" for k in _FORWARD_ENV if k in os.environ]
    argv0 = os.path.abspath(sys.argv[0])
    sys.stdout.flush()
    sys.stderr.flush()          # execvp NÃO drena os buffers do Python
    try:
        os.execvp("sudo", ["sudo", "env", f"{_ELEVATION_SENTINEL}=1",
                           f"PATH={_elevated_path()}", *forwarded,
                           sys.executable, argv0, *sys.argv[1:]])
    except OSError as e:
        # Só dispara quando o binário `sudo` não existe no PATH.
        # Falha de autenticação ou regra de sudoers acontece DEPOIS do execvp,
        # quando este processo já foi substituído — nesse caso o usuário vê a
        # mensagem do próprio sudo, não esta.
        Logger.error(f"Não foi possível elevar via sudo ({e}). "
                     f"Rode novamente como root, ou use --no-elevate.")
        sys.exit(1)
```

### O custo escondido do repasse de PATH

Este é o achado do terceiro round de review, e é a parte menos óbvia do design.

Hoje, `sudo e2fsck` funciona em Debian e Ubuntu **por causa** do `secure_path` — o PATH de usuário comum nessas distros é `/usr/local/bin:/usr/bin:/bin:/usr/local/games:/usr/games`, sem `/usr/sbin` nem `/sbin`. Quem coloca os sbin na jogada é o `secure_path` do sudo.

O design troca isso pelo PATH do chamador, e o Next Step 4 ainda remove o `sudo` de `images.py:27-28`. Resultado numa Ubuntu 24.04: `shutil.which("e2fsck")` devolve `None`, `check_system_deps()` aborta e `images.resize()` quebra.

**Não dá pra reproduzir nesta máquina.** No CachyOS, `/sbin → usr/bin` e `/usr/sbin → bin`, então os sbin já estão no PATH de qualquer usuário. É o motivo de o problema ter passado por dois rounds de review: a máquina do mantenedor é justamente a que não sofre. O probe do assignment também não pega — por isso ele ganhou um bloco que imprime o PATH pré-pixi, pra quem testar em Debian ver o buraco.

O `_elevated_path()` acima repõe os três diretórios. Vale notar que isso **aumenta** a superfície da nota de segurança: além de carregar o PATH do usuário para dentro do root, ele agora também garante os sbin. O ganho é que o comportamento passa a ser igual em toda distro; o custo é que a lista de diretórios confiáveis vira decisão do programa, não do `sudoers`.

Mecânica que sustenta o resto:

- `sudo` resolve `env` pelo `secure_path`, mas quem escreve o `PATH` do filho é o `env`, **depois**. O `secure_path` não tem como vencer. (A rev 1 deste documento tratava `secure_path` como risco; era erro meu, corrigido pelo review.)
- `sys.executable` sob pixi é caminho absoluto dentro de `.pixi/envs/default/bin`, e o Python do conda-forge descobre o próprio prefixo a partir dele. O interpretador não depende de env nenhuma.
- `f"PATH=..."` é elemento de argv, não palavra de shell. Sem risco de quoting.
- A sentinela mata o loop infinito caso o `sudo` retorne sem elevar.
- `sudo` seta `SUDO_USER`, então `get_download_dir()` e `get_data_dir()` continuam funcionando.
- `sys.argv` é repassado literalmente, então `--no-elevate` chega ao filho — inofensivo, já que o filho é root e retorna na primeira linha.

### Wiring do `--no-elevate`

A versão ingênua — declarar a flag só no parser de topo — **fica inalcançável pelas tasks do pixi**, que são o único jeito de rodar o programa segundo este mesmo documento. `pixi run install --no-elevate gapps` expande para `python main.py install --no-elevate gapps`, com a flag depois do subcomando, e o argparse rejeita.

Solução: parser-pai compartilhado, para a flag valer nos dois lados, mais um override por variável de ambiente.

```python
# main.py — parser-pai, declarado antes dos subparsers.
# default=SUPPRESS é OBRIGATÓRIO: sem ele, o subparser sobrescreve o valor
# do parser de topo com o próprio default, e `main.py --no-elevate install
# gapps` volta False em silêncio. Testado.
elevation = argparse.ArgumentParser(add_help=False)
elevation.add_argument("--no-elevate", action="store_true",
                       default=argparse.SUPPRESS,
                       help="Não se auto-elevar via sudo; aborta se não for root")

parser = argparse.ArgumentParser(parents=[elevation], ...)
# e cada subparser criado em main.py:286-345 recebe parents=[elevation]:
#   install = subparsers.add_parser('install', parents=[elevation], help=...)

# main.py:349 e main.py:352 — os dois call sites existentes.
# getattr com default, porque SUPPRESS faz o atributo não existir quando
# a flag não é passada.
no_elev = (getattr(args, "no_elevate", False)
           or os.environ.get("WAYDROID_SCRIPT_NO_ELEVATE") == "1")
helper.check_root(allow_elevate=not no_elev)
```

Verificado por teste nas cinco formas: flag antes do subcomando, depois do subcomando, ausente, sozinha (caminho `interact()`), e num subcomando diferente. As cinco dão o resultado certo.

Uso, nas três formas que passam a funcionar:

```
pixi run install --no-elevate gapps
python main.py --no-elevate install gapps
WAYDROID_SCRIPT_NO_ELEVATE=1 pixi run install gapps
```

### `check_system_deps()`

**Requer `import shutil` no topo de `tools/helper.py`.** Os imports atuais são `gzip, os, re, platform, subprocess, sys, requests, hashlib, typing.Optional` — sem `shutil`, o bloco abaixo levanta `NameError`. Está no Next Step 5.

```python
import shutil   # NOVO no topo de tools/helper.py

_ENV_REQUIRED = ("lzip", "tar")          # devem resolver dentro do prefixo
_HOST_REQUIRED = ("mount", "mountpoint", "umount", "waydroid")
_SBIN_REQUIRED = ("e2fsck", "resize2fs") # vivem em sbin, ver _elevated_path()
_HOST_OPTIONAL = ("openssl",)            # só o subcomando mitm usa

def check_system_deps():
    problems = []
    for name in _ENV_REQUIRED:
        path = shutil.which(name)
        if path is None:
            problems.append(f"{name}: não encontrado")
        elif not path.startswith(sys.prefix):
            problems.append(f"{name}: resolveu para {path}, fora de {sys.prefix}")
        else:
            Logger.info(f"{name}: {path}")
    for name in _HOST_REQUIRED:
        path = shutil.which(name)
        if path is None:
            problems.append(f"{name}: não encontrado no host")
        else:
            Logger.info(f"{name}: {path}")
    for name in _SBIN_REQUIRED:
        # busca explícita nos sbin: numa Debian/Ubuntu o PATH herdado pode
        # não tê-los, mesmo com o processo já sendo root
        path = shutil.which(name, path=_elevated_path())
        if path is None:
            problems.append(f"{name}: não encontrado nem no PATH nem em {_SBIN_DIRS}")
        else:
            Logger.info(f"{name}: {path}")
    for name in _HOST_OPTIONAL:
        Logger.info(f"{name}: {shutil.which(name) or 'ausente (só mitm precisa)'}")
    if problems:
        for p in problems:
            Logger.error(p)
        sys.exit(1)
```

Chamado logo depois de `check_root()` nos dois call sites, e **antes** de qualquer download. Aborta para `_ENV_REQUIRED`, `_HOST_REQUIRED` e `_SBIN_REQUIRED`; apenas reporta `_HOST_OPTIONAL`.

E os três `sudo` internos (`images.py:27,28` e `helper.py:58`) são removidos, já que o processo é root nesse ponto.

### Nota de segurança, explícita

Propagar `PATH` através do `sudo` derrota o `env_reset`, que existe justamente pra impedir isso. O risco concreto: um `lzip` malicioso num diretório do seu PATH roda como root.

Contexto honesto: o README atual já manda `sudo venv/bin/python3 main.py`, ou seja, já executa como root um interpretador que vive dentro do home do usuário. A superfície não é nova — fica explícita. Em desktop de usuário único é tradeoff aceitável. Deve constar no README, não ficar escondido no código.

**E o inverso precisa de aviso no README: nunca prefixe `pixi run` com `sudo`.** `sudo pixi run ...` faz o root virar dono de `.pixi/`, e todo `pixi install` seguinte quebra.

## Open Questions

**OQ-FORK — O que os forks mais recentes trouxeram de novo?**
Não é lacuna de verificação, é **item 2 de uma fila deliberada**. A ordem definida pelo mantenedor:

1. Migrar a estrutura de venv para pixi (este documento).
2. Pesquisar forks mais atuais do `casualsnek/waydroid_script` e ver o que trouxeram.
3. Ler as issues do upstream e tentar arrumá-las.

O motivo da ordem: comparar código contra uma base que ainda vai mudar gera trabalho jogado fora. Com o toolchain estável, cherry-pick de outro fork e correção de issue viram diffs limpos em vez de conflito com a migração em andamento.

Consequência aceita: se existir um fork sucessor muito ativo, parte do trabalho deste documento pode ser redundante. O mantenedor escolheu esse risco conscientemente em troca de uma base estável para comparar.

**OQ-E2FSPROGS — Confirmar que `e2fsprogs` fica no host.**
conda-forge tem `1.46.2` (2021, verificado); Arch ships 1.47.x. Rodar um `e2fsck` de 2021 sobre imagem ext4 criada por kernel atual é risco sem ganho. Inclinação forte: host. Fecha assim que alguém testar `resize` numa imagem real.

**Consequência de escolher "host", que precisa entrar junto:** `images.py:27-28` passa `ignore="^e2fsck \d+\.\d+\.\d (.+)\n$"` — regex presa a versão de três componentes com um dígito no último. Verificado: casa com `1.46.2` e `1.47.1`, **não** casa com `1.47.10`. Como `run()` levanta `CalledProcessError` para qualquer coisa em stderr que não case com `ignore`, deixar a versão solta no host agenda uma quebra futura num fsck **bem-sucedido**. Escolher "host" implica afrouxar as duas regexes para `\d+(\.\d+)*`.

**OQ-REQUIREMENTS — `requirements.txt` fica como ponte ou sai junto?**
Manter facilita quem chega por links antigos; remover elimina a segunda fonte de verdade.

**OQ-PLATAFORMAS — `linux-32` e `linux-armv7l` deixam de ser suportados.**
`helper.host()` (`tools/helper.py:110-128`, incluindo o `raise ValueError` do final, que é o que um usuário `i686` passaria a ver) mapeia `i686` e `armv7l`, mas conda-forge não tem essas plataformas. Migrar pra pixi **remove** esses usuários. Aceitar e documentar, ou manter um caminho `requirements.txt` só pra eles?

**OQ-DOAS — `doas` / `run0` em vez de `sudo`.**
A re-execução assume `sudo` no host. Sem `sudo` no PATH, o `except OSError` degrada com mensagem clara; com `sudo` presente mas negando, quem fala é o sudo.

**OQ-SECUREPATH — `secure_path` está configurado nesta máquina?**
`/etc/sudoers` é 0440, não deu pra ler. Se `secure_path` **não** estiver setado, `env_reset` preserva o `PATH` do chamador e os dois lados do probe do assignment vão concordar — o que seria falso alarme, não falha de premissa. O probe abaixo distingue os dois casos.

**OQ-TLS — FECHADA, sem risco.**
Hipótese anterior: `SSL_CERT_FILE`/`SSL_CERT_DIR` setados pela ativação do pixi seriam descartados pelo `env_reset`, quebrando o `requests` em `helper.py:92`. Verificado: `pixi run sh -c 'env | grep SSL_CERT'` não retorna nada — o pixi não seta nenhuma das duas. O Python do conda resolve pelo `certifi` que vive dentro do próprio env, por caminho absoluto. Não depende de variável de ambiente, logo `env_reset` não tem como quebrar. Se uma versão futura do pixi passar a exportá-las, adicionar ao `_FORWARD_ENV` é mudança de uma palavra.

## The Assignment

Salve como `probe.sh` na raiz do repositório e rode `pixi run sh probe.sh`.

Antes, **fora** do pixi, uma linha só:

```
echo "$PATH" | tr ':' '\n' | grep -c sbin
```

Se devolver `0`, você está numa distro onde o PATH de usuário comum não tem `/usr/sbin` nem `/sbin` — é o buraco descrito em "O custo escondido do repasse de PATH", e é o caso de Debian e Ubuntu. No CachyOS devolve um número maior que zero, porque `/sbin → usr/bin`.

Depois, o script:

```sh
#!/bin/sh
echo "=== 1. PATH dentro do pixi ==="
echo "$PATH" | tr ':' '\n' | head -3

echo "=== 2. PATH que o sudo entrega (secure_path configurado?) ==="
sudo sh -c 'echo "$PATH"' | tr ':' '\n' | head -3

echo "=== 3. com PATH repassado (o que o design faz) ==="
sudo env "PATH=$PATH" sh -c 'command -v lzip; command -v tar'

echo "=== 4. reentrando no sudo (o que images.py:27 faz hoje) ==="
sudo env "PATH=$PATH" sh -c 'sudo sh -c "command -v lzip; command -v tar; command -v e2fsck"'

echo "=== 5. TLS do requests sob PATH repassado ==="
sudo env "PATH=$PATH" python -c "import requests; print(requests.get('https://f-droid.org', timeout=10).status_code)"
```

**Use arquivo, não one-liner.** `pixi run` não entrega o comando ao seu shell: ele passa pelo `deno_task_shell` primeiro, e o probe atravessa até três níveis de shell aninhados. Duas versões anteriores deste probe morreram no quoting antes de rodar. Rodando `sh probe.sh`, o deno_task_shell só precisa entender duas palavras e o resto é `/bin/sh` de verdade.

(A rev 3 deste documento afirmava que o `deno_task_shell` "não parseia aninhamento de aspas como POSIX". O review testou e mostrou que a versão aninhada roda sim no pixi 0.55 — a generalização veio de uma tentativa que falhou por outro motivo. O conselho continua valendo; a justificativa era falsa.)

Outras duas armadilhas já pagas: `command` é builtin, não existe `/usr/bin/command` — `sudo command -v` sai com 127, por isso tudo vive dentro de `sh -c`. E `command -v` é POSIX com **um** operando: no `dash` (o `/bin/sh` de Debian e Ubuntu) `command -v lzip tar` imprime só o primeiro e engole o segundo calado.

### O que esperar

A estrutura já foi testada localmente, substituindo o `sudo` por um stub que simula `secure_path`. O resultado:

| Bloco | `lzip` | `tar` | `e2fsck` |
|---|---|---|---|
| 3 — PATH repassado | `.pixi/envs/default/bin/lzip` | do env (o `pixi.toml` inclui `tar`) | — |
| 4 — reentrando no `sudo` | **não encontrado** | `/usr/bin/tar` | `/usr/bin/e2fsck` |

Bloco 5 devolveu `200`.

O que ler em cada bloco:

1. **Bloco 2 fecha a OQ-SECUREPATH.** Se o PATH que o sudo entrega for `/usr/local/sbin:/usr/local/bin:/usr/bin` ou parecido, `secure_path` está configurado. Se vier igual ao seu, não está — e aí os blocos 3 e 4 concordam, o que é *esperado*, não falha de premissa.
2. **Bloco 3 é linha de base, não teste.** O `env` escreve o PATH depois do `sudo`; não tem como falhar.
3. **Bloco 4 é o achado.** Reentra no `sudo` exatamente como `images.py:27` e `helper.py:58` fazem hoje. É o bug que o Next Step 4 conserta.
4. **Bloco 5 confirma a OQ-TLS** já fechada por argumento — agora com número.

### O detalhe que o teste revelou

Sob `sudo` aninhado o `lzip` não resolve para a versão errada: **não resolve para nada**, porque não existe no host desta máquina. Isso divide o risco em dois:

- **`lzip` falha alto.** Qualquer usuário sem `lzip` de distro vê `tar --lzip` explodir na hora. Barulhento, fácil de diagnosticar.
- **`tar` e `e2fsck` falham em silêncio.** Existem no host, então resolvem — só que para a versão do host, não a do lockfile. Nada quebra, nada avisa, e a reprodutibilidade que a migração prometeu simplesmente não existe.

O segundo caso é o que justifica o Next Step 4 e o Critério 9. É também o motivo de `e2fsprogs` ficar fora do `pixi.toml`: colocá-lo lá criaria a ilusão de que está pinado.

## A reversão, e por quê

O corpo acima constrói auto-elevação, propagação de PATH, reposição de sbin, flag
`--no-elevate`, sentinela anti-loop e uma regressão de segurança documentada — tudo para
garantir que `lzip` e `tar` venham do lockfile e não do host.

Nada disso é necessário. Basta chamá-los por caminho absoluto.

Verificado nesta máquina, que não tem `lzip` no host:

```
A) /usr/bin/tar --lzip -xf t.tar.lz                              (PATH=/usr/bin:/bin)
   → tar (child): lzip: Cannot exec: No such file or directory   → FALHOU

B) /usr/bin/tar --use-compress-program=<abs>/lzip -xf t.tar.lz   (mesmo PATH pelado)
   → extraiu
```

Detalhe que a voz externa errou e o probe corrigiu: `tar` absoluto **não basta** — o próprio
GNU tar procura `lzip` no PATH quando recebe `--lzip`. É preciso `--use-compress-program`
com caminho absoluto.

Com isso, `sudo` mantém o `secure_path` intacto e `e2fsck`, `resize2fs`, `mount`,
`mountpoint`, `umount` e `waydroid` continuam resolvendo como hoje. A garantia sobre
`lzip`/`tar` fica **mais forte** que a original: caminho absoluto não pode ser derrotado
por PATH nenhum.

```
ANTES (Approach C)                        DEPOIS (caminho absoluto)
─────────────────────────                 ──────────────────────────
pixi run install gapps                    pixi run install gapps
  └─ python main.py                         └─ task: sudo <abs python> main.py install
      └─ check_root() → execvp                  └─ (já é root, check_root() só valida)
          └─ sudo env PATH=<user+sbin>              └─ secure_path do sudo, intacto
              └─ python main.py (de novo)          └─ tar -I <abs lzip>  ← garantido
                  └─ tar --lzip  ← torce pro PATH
```

Some: `_elevated_path()`, `_SBIN_DIRS`, a inversão do `check_root()`, `--no-elevate`,
a cirurgia de parser-pai para ele, a sentinela, a nota de segurança sobre `env_reset`,
OQ-SECUREPATH, OQ-DOAS, o Critério 13 e o Assignment.
